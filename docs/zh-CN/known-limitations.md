# 已知限制

[English](../known-limitations.md) · **中文**

Xtate v2.15.2 围绕一个刻意的取舍构建：极高的报文速率与低廉的逐目标成本，代价是可靠性和协议完整性。本页列出当前版本不做什么、这对你的结果意味着什么，以及如何规避。

这些限制背后的机制见 [ZBanner](./zbanner.md)、[HLTCP](./hltcp.md) 和[架构](./architecture.md)。以下内容均已对照 v2.15.2 源码核对。

| 领域 | v2.15.2 中的主要限制 | 规避方式 |
|:---|:---|:---|
| ZBanner | 没有逐目标超时，也不重传 | 重跑该范围并合并结果 |
| `tcp-state` | 只报告开放端口；SYN 不重传 | 用 `tcp-syn` 做覆盖，用 `tcp-state` 取证 |
| IPv6 | 分片与大多数扩展头会被丢弃 | 避免分片路径，按 /64 分段扫描 |
| Windows | 无 PF_RING/`sendmmsg`，无法抑制 RST | 在 Linux 上做 banner 扫描 |
| 输出 | 同一时刻只能用一个输出端；默认转义不是合法 JSON | 先写本地 text/NDJSON，再导入 |

## ZBanner（无状态 TCP）

适用于 v2.15.2，覆盖整条 `zbanner` 扫描链路。

- **没有逐目标超时，也不重传。** SYN 或 banner 报文段一旦丢失，该目标就是没有结果；不会有任何重试，也不存在超时表。规避方式：重跑该范围（`--repeat 1`，或用不同的 `-seed` 再完整跑一遍）并合并结果。
- **去重是近似的。** 去重表是固定大小的 4 路桶加随机老化（默认 `-dedup-win 1000000`，约 70 MB），且 IPv4 哈希只用到地址低位。高负载下条目会被挤出，`repeats` 计数随之失真。影响：重复结果抑制只能尽力而为，任何依赖 `repeats` 的功能（尤其是 `--all-banner` 的编号以及 `-all-banner-limit`/`-all-banner-floor`）在互联网规模下都不可靠。规避方式：调大 `-dedup-win`，并且不要把 `repeats` 当作精确计数。
- **`--all-banner` 是启发式，不是流重组器。** 后续报文段按数据长度确认并去重；乱序报文段不会被排序，段序号来自近似的去重计数。影响：长 banner 可能被截断或编号错乱。规避方式：保持响应较小、调大 `-tcp-win`，或改用 `tcp-state` 获取完整 TLS/HTTP 内容。
- **默认在第一个 banner 报文段之后就关闭连接。** 多段响应（大的 TLS ServerHello、证书链、很长的 HTTP 头）会被截断，除非你传入 `-scan-arg "-all-banner"`。
- **探测载荷受包缓冲大小限制。** 载荷必须和 IP/TCP 头一起塞进 2048 字节的包（实际约 2000 字节载荷）。超限时不会截断——整个包不会发出，也不会报错。规避方式：把探测载荷控制在约 2000 字节以内。
- **零窗口 SYN-ACK 会被判成 `fake-open`**，并且不会收到探测载荷。SYN 队列已满的真实服务也可能看起来像 fake open。规避方式：v2.15.2 中没有；把 `fake-open` 当作"稍后重试"，而不是端口关闭。
- **banner 扫描在 Linux 上依赖主机全局防火墙规则。** ZBanner 依赖内核不去应答未知连接；随仓库提供的脚本在安装期间会丢弃本机*所有*出向 TCP RST。v2.15.2 的生产路径中没有进程内 RST 过滤。忘记执行 `./firewall/rm_rules.sh` 会让本机持续丢弃所有出向 RST，TCP 重置从此失效。
- **v2.15.2 没有随附这些规则的 Windows 等价物**，因此从 Windows 发起基于握手的 banner 扫描并不可靠。
- **输出是事件式的，不是按目标聚合的。** 一个目标可能产生一行 `open`、多行 `banner` 以及一行 `acknowledged`。下游使用方必须自己按目标/端口聚合。
- **握手之后使用 1024 字节的窗口**（默认 `-tcp-win`），这限制了在途数据量，并促使对端拆成小段发送。规避方式：调大 `-tcp-win`（多段数据同时用 `--all-banner`）。
- **cookie 强度是测量级的，不是认证级的。** 32 位 SipHash cookie 加上确定性的源端口（`-src-port` 起始值 + probe 序号）足以让回包相对于友好对端可验证，但对知道种子的路径外攻击者是可预测的。
- **多 probe 需要足够的源端口余量。** 多 probe 模块的每个 probe 槽位占用源端口区间中的一个端口（`-src-port`，默认 256 个端口）；如果区间比 probe 数量还小，多出来的槽位会落到区间之外，其回包被静默丢弃。规避方式：扩大 `-src-port`。

## ZBanner 之外的无状态扫描模块

适用于 v2.15.2，涉及 `tcp-syn`、`udp`、各 ICMP 扫描、`arp-req`、`ndp-ns`、`sctp-init` 以及 Yarrp 系列模块。

- **内置 BPF 过滤器是字面匹配，可能过窄。** `tcp-syn` 的过滤器精确匹配裸 RST（`tcp[tcpflags]==tcp-rst`），而部分协议栈会用 RST+ACK 回应关闭端口；这类回包可能永远到不了用户态校验环节。影响：关闭端口可能毫无报错地缺失。规避方式：用 `--no-bpf` 验证，或提供更宽的 `--bpf-filter`。
- **UDP、ARP 和 NDP 没有 cookie 校验。** UDP 回包只靠目标集合包含性加探测模块自身的回调来验证；ARP/NDP 还需要默认的 `blackrock` 生成模块来反查目标集合。换成其他生成模块后，ARP/NDP 会退化成"任何回包都算数"，UDP 则失去关闭端口判定。
- **ICMP 标识位太短。** `icmp-echo`/`icmp-time` 只在 ICMP id 里放了 8 位 cookie（sequence 字段里再放 8 位），因此误归属的概率远高于 TCP 的 32 位 cookie。
- **Yarrp 去重可能把不同目标合并。** 逐跳结果按外层源地址和 TTL 去重；同一路由器后、距离相同的不同目的地址可能被判为重复而丢弃。影响：多目标拓扑测量会丢路径。规避方式：缩小批次，或接受损失再做后处理。
- **分片 IP 报文在校验之前就被丢弃**——IPv4 带 MF/分片偏移的，以及 IPv6 带分片头的。启用 `--no-bpf` 也不会改变这一点。

## HLTCP / `tcp-state`（混合状态 TCP）

适用于 v2.15.2，涉及 `tcp-state` 扫描以及所有 `*-state` 探测模块。

- **只有三个 TCP 状态**（SYN-SENT、SENDING、RECEIVING）。没有 LISTEN、FIN-WAIT、CLOSE-WAIT、TIME-WAIT，没有优雅关闭，对端 FIN 一律用 RST 回应。影响：部分服务器会记录异常终止日志，半关闭交互也无法建模。
- **SYN 只发一次，不重传。** SYN 丢失意味着该目标没有任何输出。规避方式：降低速率、用 `--repeat` 重跑，或在大范围覆盖时优先用 `zbanner`。
- **ACK 丢失后不重发。** 重复的 SYN-ACK 会被忽略而不是重新确认，连接最终由 `tcp-state` 自己的连接过期机制回收（`-scan-arg "-conn-expire 30"`，默认 30 秒）。
- **RTO 固定为 1 秒**，没有 RTT 估计，也没有指数退避。高延迟路径会浪费时间和带宽。规避方式：尽量选低延迟的观测点。
- **没有乱序重组。** 超出期望序号的数据会被丢弃，协议栈会等待对端自己重传；丢包路径上的大段 TLS 数据可能永远无法完成。规避方式：把速率压低到不丢包，或接受交换不完整。
- **关闭端口永远不报告。** 未知连接的 RST 没有 TCB，会被直接丢弃，所以 `tcp-state` 的输出里只有开放端口。需要开放/关闭判定就用 `tcp-syn`。
- **TLS 不发送 SNI，也不发送 ALPN。** `tls-state` 发出的 ClientHello 不带服务器名，也不做协议协商：CDN 和虚拟主机会用默认证书/默认站点应答，HTTP/2 永远不会被协商。影响：证书可能属于完全不同的主机名。规避方式：v2.15.2 中没有——直接扫描源站 IP，或者只关心 Hello 级指纹时改用 `zbanner` 搭配 `tls-hello`。
- **关闭是 RST，而不是 `close_notify`。** TLS 会话被 TCP reset 拆掉，对端永远看不到一次干净的 TLS 关闭。
- **内存随 OpenSSL 增长。** 纯 HLTCP 连接只占几百字节，但 TLS 会话会叠加 OpenSSL 状态（每连接通常几 KB 到几十 KB，大头是 `SSL*`/证书），此外每个处理线程还有固定的 TCP 表和计时轮（约 8 MiB/处理线程）。TCB 在池中循环复用，进程退出前不会归还给操作系统。
- **接收侧去重对 `tcp-state` 关闭**；正确性依赖状态机幂等，这也让上面的 ACK 丢失问题更容易暴露。
- **多 probe 连接共享源端口空间。** 每个 probe 槽位映射到一个源端口，因此 probe 数量必须小于 `-src-port` 区间，否则不同槽位的连接会串线。

## IPv6

适用于 v2.15.2，涉及所有 IPv6 扫描。

- **只理解逐跳（hop-by-hop）扩展头。** 目的选项头、路由头，以及最关键的——分片头，都会让报文在进入扫描逻辑之前被丢弃（`--no-bpf` 也没用）。规避方式：避开需要分片的 IPv6 路径；降低速率，谨慎使用对 MTU 敏感的探测。
- **源地址池只覆盖 IPv6 地址区间的低 64 位**，且必须共享相同的高 64 位；链路本地源地址必须显式指定。规避方式：按 /64 分别扫描。
- **`-src-ip` 区间大小必须是 2 的幂**，与 IPv4 完全一致。
- **IPv6 不记录 IPID**（它本来就不存在）；`-scan-arg "-ipid"` 只影响 IPv4 结果。
- **扫描空间受 63 位上限约束**（默认 `blackrock` 生成模块，按地址 × 端口计）。大规模 IPv6 普查必须用 `--shard` 或更窄的前缀拆分。
- **`icmp-time` 和 `arp-req` 仅支持 IPv4**；IPv6 请用 `ndp-ns` 和 `icmp-echo`。

## Windows

适用于 v2.15.2，涉及 Windows 构建。

- **没有 PF_RING，也没有 `sendmmsg`/AF_PACKET 路径。** 发送只能走 Npcap 的 send-queue 或逐包发送；`--send-queue` 能显著提高速率但会增加延迟，所以对 `zbanner`/`tcp-state` 请保持关闭。
- **接收是阻塞的**（`pcap_next_ex`）；Windows 上没有非阻塞网卡模式，因此慢速输出端或极高速率都会表现为丢回包。
- **交互模式无法自我重启。** Linux 上交互式扫描会用 `recover.conf` 重新执行自身；Windows 上 `-interact` 在扫描结束后就返回，需要手动再启动。
- **网卡名不友好。** 用 `--list-if` 打印的数字编号（例如 `-if 3`），而不是 Npcap 的完整设备名。
- **基于握手的 banner 扫描没有内核 RST 抑制手段**（防火墙脚本只针对 `iptables`/`ip6tables`）。

## 输出与 I/O

适用于 v2.15.2，涉及所有平台。

- **同一时刻只能启用一个输出模块（OutputModule）**，且写出发生在处理线程内、由一把全局互斥锁串行化。慢速输出端（走网络的 MongoDB、慢磁盘）会拖慢整次扫描。规避方式：先写本地 text/NDJSON，再导入。
- **默认字符串转义不符合 JSON 规范。** 引号、反斜杠和控制字符会变成 `\xNN`；当下游是 JSON 解析器时请加 `--no-escape-char`。BSON/MongoDB 模块必须保持默认模式。
- **`classification` 和 `reason` 被 CSV/NDJSON 写出器原样输出**，因此引号或换行可能破坏一条记录。规避方式：优先用 BSON，或在下游清洗这些字段。
- **`--max-packet-len` 默认 1514 字节**；更大的接收帧会被整体忽略（不只是截断）。面对巨帧、隧道或大 TLS 记录时，要连同 `--adapter-snaplen` 一起调大。
- **`--pcap` 只保存收到的报文**，它不是回放设施；发出的报文不会出现在文件里。

## 框架与规模

适用于 v2.15.2，涉及所有平台。

- **模块在编译期注册。** 没有运行时插件加载：新增模块意味着改注册表并重新构建。可选依赖（OpenSSL、PCRE2、LibXml2、libbson、libmongoc）会在构建时把对应模块从二进制里去掉。
- **Lua 探测模块在运行时加载**，因此缺少 `liblua` 的表现是 `lua-tcp`/`lua-udp` 启动失败，而不是模块缺失。规避方式：安装 Lua 5.3/5.4。
- **只有一个接收线程**，去重也在这个线程里。Rx 侧吞吐无法靠加线程扩展；只能用多台主机或 `--shard`。
- **超大规模 IPv4 普查需要显式确认。** 目标 IP 超过 1,000,000,000 且没有 `--exclude` 时会在启动阶段被拒绝；`--exclude 255.255.255.255` 是文档给出的确认方式。
- **默认生成模块在整个扫描空间上随机化。** `--shard` 只对默认的 `blackrock` 生成模块有文档保证；`--resume`（重新载入已保存的配置）和 `--resume-index`（从绝对扫描索引开始）都假设目标可按索引寻址，这一点只对默认生成模块成立。

## 用好 v2.15.2

用 `tcp-syn` 做覆盖与开放/关闭判定，用 `zbanner` 做大范围无状态 banner 抓取，用 `tcp-state` 处理少量高价值的 TLS/HTTP 目标。只在需要的扫描前后添加防火墙规则，保持载荷和速率克制；选探测模块之前，先读[扫描模式](./scanning-modes.md)里的模块级限制。
