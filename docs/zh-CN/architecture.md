# 架构

[English](../architecture.md) · **中文**

Xtate 是一款模块化的全栈网络扫描器，面向大规模主动测量。它把一次扫描拆成由四类可插拔模块组成的流水线——**生成**（目标）、**扫描**（L3/L4 报文）、**探测**（L5 及以上载荷与解析器）和**输出**（结果）——并让这条流水线跑在少量固定线程上。运行期不加载任何东西：每个模块都是以 NULL 结尾的注册表里的一个静态结构体，缺少可选依赖库的模块会在编译期被裁掉。

流水线上方是两个引擎，它们才是这个项目存在的理由：

- **ZBanner**——无状态 TCP 握手，不需要每目标连接表就能拿到真实 banner。见 [zbanner.md](./zbanner.md)。
- **HLTCP**——混合状态用户态 TCP 栈，能完成 TLS 握手，并在其中收发 HTTP。见 [hltcp.md](./hltcp.md)。

本文介绍两个引擎共用的机制。

## 扫描流水线

一次扫描朝一个方向推进：目标被生成，构造成报文发出，回包被解析并归约为结果。

1. **生成**产出下一个目标——一个 `(ip_them, port_them, ip_me, port_me, ip_proto)` 元组，由目标集合展平并打乱后得到。
2. **扫描**为该目标构造报文，交给 raw socket 层。
3. **探测**贡献应用层载荷，并解释响应。
4. **输出**把每个结果格式化为一个 `OutItem`，写到你指定的地方。

在互联网规模下，发送与接收不能共用一个线程，因此流水线被拆到多个线程上，各阶段之间用无锁环形队列连接。

## 线程模型

![Xtate 线程模型：N 个发送线程、1 个接收线程、1 个分发线程，以及 M 个各自持有 TCB 表的处理线程，通过 NetStack 回注队列连接](../../screenshots/architecture.svg)

一次运行中的扫描共有 **N + M + 3** 个线程：1 个主线程、N 个发送线程、1 个接收线程、1 个分发线程和 M 个处理线程。在默认的 `--tx-thread-count 1` 与 `--rx-handler-count 1` 下就是五个线程。

| 线程 | 数量 | 创建者 | 职责 |
|:---|:---:|:---|:---|
| main | 1 | 操作系统 | 控制面：解析配置、初始化模块、轮询状态、处理信号、排空并退出。不在报文路径上。 |
| tx | N | main | 从生成器取目标、构造报文、发送，并冲刷处理线程排入的后续报文。 |
| rx | 1 | main | 接收、预处理并校验每个回包；按需写入 pcap；可选去重；分发。 |
| dispatch | 1 | rx | 对源 IP 做哈希，把报文放入 M 个处理队列之一。 |
| handle | M | rx | 运行扫描/探测状态机，格式化结果，并排队后续报文。 |

这样拆分是因为两半的约束不同。发送侧受速率整形，瓶颈在报文构造的 CPU；接收侧受 I/O 约束，不能被每连接的处理拖慢。处理线程承载昂贵的每目标逻辑，所以当有状态扫描需要更多 CPU 时，这里是唯一需要横向扩展的线程池。

**分发亲和性。** 分发线程计算 `hash(src_ip) & (M - 1)`，投递到 `handle_q[0..M-1]`。由于哈希只使用源 IP，来自同一主机的每个报文都会按到达顺序落到同一个处理线程。正是这一个决定让有状态扫描可以无锁运行：一个处理线程独占自己的连接，因此一个 TCB 永远只有一个写者。`M` 必须是 2 的幂且不超过 256：哈希只有 8 位宽，更大的掩码会让多出来的处理队列永远收不到流量；更大的值会在启动时被拒绝。

**每处理线程的连接表。** `tcp-state` 这类有状态扫描会为每个处理线程分配一张用户态 TCP 连接表，而不是一张全局表。上面的亲和性规则保证不会有两条线程碰同一条连接，所以快路径不需要互斥锁。代价是连接状态与线程绑定：调整 `M` 会改变连接的分布。

**NetStack 队列。** 处理线程不直接发包。后续报文——一个 ACK、一个 RST、下一个探测——会写进名为 `transmit_queue` 的共享环形队列；发送线程在每轮循环开头、生成新目标之前冲刷它。同一套机制还共享一个定长包缓冲池（每块 2048 字节）。这正是让无状态接收路径驱动真实 TCP 会话的技巧：接收侧保持纯粹，而有状态决策被表达为排队待发的报文。分发队列与处理队列在启动时定容（默认 16384 个槽位，2 的幂）。队列满时生产者睡眠重试而不是丢弃——扫描器施加的是背压，不是丢包。

CPU 亲和性按固定顺序分配——先发送线程，再接收线程，最后处理线程——可用 `--no-cpu-bind` 关闭。

## 四类模块

| 类型 | 拥有什么 | 调用来源 |
|:---|:---|:---|
| 生成 | 目标序列及置换状态 | 发送线程 |
| 扫描 | 报文构造与扫描级状态机 | tx（`transmit`）、rx（`validate`）、handle（`handle`、`poll`） |
| 探测 | 载荷字节、响应解析、可选的每连接会话 | tx 或 handle（`make_payload`）、rx（`get_payload_length`）、handle（`handle_response`、状态回调） |
| 输出 | 结果格式化与投递 | 处理线程，由一把锁串行化 |

每类接口都是一小组回调，并明确标注了线程归属。一个扫描模块会三次看到同一个回包：在 `validate` 里判断这个包是不是你的、是否应当去重；在 `handle` 里运行状态机并产出结果；在 `poll` 里处理超时（处理线程每轮循环都会调用）。探测模块有两种形态：无状态（输入载荷、输出字节）和有状态（一个会话，含 `conn_init` / `make_hello` / `parse_response` / `conn_close`，始终在拥有该连接的处理线程上调用）。

四张注册表就是普通的 C 数组，所以新增模块只需要写一个结构体和一行注册。同一份元数据驱动 `--list-*`、`--help-*`、参数解析、模糊搜索和交互式补全。没有插件 ABI，也没有运行时发现。

## 报文构造

报文不是每个目标从头构造的。启动时模板层会预先构造一小组报文模板——SYN、带数据的通用 TCP、RST，以及 UDP、ICMP、ARP、NDP、SCTP 的对应模板——发送时按目标把地址、端口、序号和 IP ID 修补进副本，再重算传输层与 IP 校验和。不同模板携带不同假设：SYN 模板通告 MSS 1460 和 64240 字节窗口，非 SYN 的 TCP 模板不带选项、窗口 1024 字节，RST 模板通告零窗口。这些默认值正是 `tcp-state` 能用 `--tcp-win` 和 `--tcp-mss` 调优的原因。

## 目标空间与随机化

目标集合被展平成 `ip × port` 的一维索引空间，并按置换后的顺序遍历。默认生成器是 **BlackRock**，一种无状态、类 DES 的置换：给定种子和索引就能算出打乱后的索引，无需存储列表，因此无论扫描多大，内存都保持平坦。该空间限制为 63 位；若请求超过十亿个地址又没有显式 `--exclude`，会被拒绝，以免误扫整个互联网。

源地址和源端口可以在各自区间内随机化。源端口区间值得留意：ZBanner 和 HLTCP 都把探测槽位编码进源端口（`first + index`），回包正是靠它对应到产生它的那次探测。因此 `--source-port` 的区间宽度至少要等于探测模块的 `multi_num`，否则多探测的回包会被过滤掉。`--shard` 与 `--resume-index` 把一次逻辑扫描拆分到多个进程和多个重启点上，两者都建立在同一套置换之上。

## 结果

每个结果都是一个 `OutItem`：目标元组、级别（`info`、`failure` 或 `success`）、`classification` 与 `reason` 字符串，外加三条带类型的键值链——分别承载扫描字段、探测字段和输出字段。输出模块只选一次，接收来自任意处理线程的结果；一把互斥锁把这些调用串行化，因此一个慢速下游（例如同步写数据库）会拖慢处理。这是刻意做出的简化取舍，也是吞吐敏感的扫描应当优先选择本地格式的原因。

## 两个引擎，一条流水线

| | ZBanner | HLTCP |
|:---|:---|:---|
| 状态 | 每目标无状态 | SYN-ACK 之后建立 TCB |
| 发送 | 先 SYN，再发携带探测载荷的 ACK | 一次完整的 TCP 会话 |
| 返回 | open/closed 与首个 banner | TLS 握手、证书、TLS 之上的 HTTP |
| 模块 | `-scan zbanner` | `-scan tcp-state` |
| 详情 | [zbanner.md](./zbanner.md) | [hltcp.md](./hltcp.md) |

两个引擎都依赖同样的两条基础设施不变量：后续报文走 NetStack 队列而不是原地发送；必须阻止本机内核对它不认识的连接回 RST。两者都需要的防火墙配置见 [zbanner.md](./zbanner.md)。

## 设计上主动放弃的东西

- **只有一个接收线程。** 接收侧处理、校验与去重从构造上就是单线程的。这让保序和去重保持简单，但也封住了接收侧吞吐上限，是链路很快时最先该剖析的地方。
- **没有输出队列。** 结果在处理线程内、持一把全局锁发出。没有独立的写线程，也没有缓冲来吸收慢速下游。
- **状态与线程绑定。** 连接状态无法在处理线程之间迁移，因此容量和延迟取决于每线程表的大小，而不是一份全局预算。
- **静态模块。** 可选功能是编译期决定；缺一个库就移除对应模块，而不是在运行时报错。

这些不是缺陷——每一条都在另一栏换来了东西。把它们写出来，是为了当扫描行为不符合预期时，你能判断自己正在为扫描器的哪一部分付出代价。
