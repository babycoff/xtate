# Xtate 3.0.0-rc.4

This is a **release candidate** for hands-on trial, not the final 3.0.0. The
final release waits for user testing and fixes.

RC.4 focuses on making the browser console usable as a real scanning tool:
clear language, Xtate's own module taxonomy, inspectable module details,
controlled scan-wide parameters, and per-run result folders.

## Changes since 3.0.0-rc.3

### Console language and structure

- The whole console switches between **English** and **中文** from the top bar.
  The choice is stored in the browser and can be forced with `?lang=en` or
  `?lang=zh`.
- Module and global-parameter descriptions use the same translated help catalog
  as `--help` and the manuals.
- Page headings are direct: **New scan**, **Live scan**, **Results**,
  **Interfaces**, **Modules**, **System**. The decorative "Point, check, send"
  headline is gone.
- Module groups use Xtate's names: **Scan modules**, **Probe modules**,
  **Output modules**, **Generate modules**.

### Module and parameter inspection

- Module cards expand in place to show the full description and a parameter
  table with name, type, description and aliases.
- The catalog is searchable across descriptions and parameter names.
  `?expand=<module>` opens a module directly.
- **Global parameters** exposes 23 safe scan-wide options (seed, packet TTL, TCP
  window/MSS, buffer sizing, dedup and similar), with search, descriptions and
  validation. Values are sent as `global_args`.
- Process, file, script, control-plane/job and GUI-overlapping options are not
  exposed. Preflight rejects unknown, wrong-type or out-of-range values before
  a worker starts.

### Results and files

- Every scan gets its own managed folder:
  `runs/<YYYYMMDD-HHMMSS>-<seq>/` with `scan.ndjson`, `scan.ndjson.log`, the
  manifest and the index. Run time is shown in Live and Results, so repeated
  scans remain distinguishable.
- On Windows the state directory is the visible `xtate-state` folder beside
  `xtate.exe`; Linux uses `$XDG_STATE_HOME/xtate` (with documented fallbacks).
  Request files are removed when a job ends.
- **Open log** / **Open result** continue to use a server-resolved job path, and
  the elevated-browser prompt is avoided by opening the console through Explorer.

### Verification

- Windows MSVC release build, self-test and full Windows suite pass: i18n
  parity/coverage, schema/module validation, JSON schema runtime, generate,
  control, MCP, MCP stability, TUI and GUI.
- Linux build with ngtcp2/GnuTLS reports `http3:true` and
  `quic_transport:true`; the Linux suite passes the same runtime checks
  (schema/module validators are Windows-only in this environment).
- GUI tests cover the language switch, translated modules/options, global
  parameter preflight accept/reject cases, per-run result folders, result
  paging, open-file rejection cases and private-token enforcement.
- Documentation link checks pass for the English and Chinese manuals.

## Compatibility

- CLI and MCP request shapes are unchanged. `global_args` is validated against
  a fixed allowlist.
- Result files supplied through `result_path` keep their existing behavior;
  omitted paths now resolve into the managed run folder.
- TUI remains deprecated in 3.0.

## Known limitations

- HTTP/3 and QUIC transport remain Linux-only; Windows reports them unavailable
  through `--list-capabilities`, MCP and the console.
- Preflight is authoritative for the fields it validates, but it does not bind a
  request hash to `job.start` yet.
- Module argument names/values are passed to the worker; they are not all
  preflight-validated. Global parameters are.
- `include_file` route grouping and MCP generate/stream input remain future
  work.
- The console does not provide per-job disk quota controls or a byte-level
  result editor.
- The final 3.0.0 is not released. Please trial RC.4 and report defects.
