# Xtate 2.44.2 release notes

Released 2026-11-13.

## Highlights

### TUN/VPN adapters now use the correct RAW link type

Xtate defined its stub `PCAP_DLT_RAW` as `101`, the `LINKTYPE_RAW` value used in
pcap savefiles. `pcap_datalink()` returns the DLT value instead, and Npcap reports
`DLT_RAW` as `12` for TUN/VPN adapters. The mismatch made a supported RAW adapter
fail with:

```text
unknown data link type: 12(RAW)
```

`PCAP_DLT_RAW` is now `12`, with a comment explaining the DLT/LINKTYPE namespace
difference. Adapters that expose IP packets directly, including Clash/Meta-style
fake-IP TUN interfaces, can now be selected and used for raw scans when the
target actually routes through that adapter.

### Link-type preflight for `--explain-target` and scan startup

`--explain-target` now prints the selected adapter's link type, for example:

```text
Interface: \Device\NPF_{...}
Link type: RAW (12)
Note: RAW link sends IP packets without an Ethernet header; MAC and ARP are not used.
Check: OK
```

If the selected adapter uses a link type that cannot carry raw IP packets, the
output includes a warning and `Check: FAIL (unsupported link type)`, and the
command exits non-zero. Scan startup applies the same rule instead of continuing
with a broken capture setup.

The multiple-default-interface error now points at the diagnostic commands:

```text
multiple default interfaces detected (2); use -if to choose explicitly
hint: run "--explain-target=<target>" to see the route and link type
hint: run "--list-if" to list adapter IDs and addresses
```

Xtate still does not silently choose one of several default interfaces. Select the
physical adapter with `-if`, especially when a VPN/TUN adapter also has a default
route.

### Scan startup shows the configured rate

The pre-scan banner and `--meta-filename` file now include the effective rate, so
the default or `--rate` value is visible before packets are sent:

```text
Scanner:    zbanner
Probe:      http
Generator:  blackrock
Interface:  3
Rate:       1000 packets/sec
IP version: v4
Scanning 1 targets
```

The value is shown exactly as configured, including the default rate when
`--rate` is omitted.

### Documentation

- `docs/troubleshooting.md` and the Chinese translation now explain fake-IP DNS,
  TUN/VPN adapters, RAW link type, and a four-step no-result checklist.
- Current-version documentation is updated to 2.44.2.

## Compatibility

- No CLI, MCP or control-plane request format changes.
- RAW-capable TUN/VPN adapters are now accepted instead of failing with
  `unknown data link type: 12(RAW)`.
- Unsupported link types now fail during preflight/startup with `Check: FAIL` or
  `cannot carry raw IP packets` instead of starting with a broken capture path.
- Version strings, `--version` and MCP `serverInfo.version` report `2.44.2`.

## Known limitations

- A fake-IP address is not the target's real address. Resolve the real address via
  DoH or configure the proxy to exclude the target, then scan the real address.
- Some VPN modes expose link types that cannot carry raw IP packets. Preflight with
  `--explain-target` and select an Ethernet/Wi-Fi adapter when needed.
- A TUN adapter may accept the packet while the remote side drops traffic for
  policy reasons; link-type success does not guarantee application response.
- The multiple-default-interface rule is unchanged: pass `-if` explicitly when more
  than one adapter has a default route.
- `--check` is a flag. To diagnose a specific target, use
  `--explain-target=<target> --check`; `--check=<target>` is parsed as a flag.

## Upgrade notes

No migration is required. If a script depended on `unknown data link type: 12(RAW)`
as a failure signal, update it to use the new preflight result. When more than one
default interface exists, keep passing an explicit `-if`.
