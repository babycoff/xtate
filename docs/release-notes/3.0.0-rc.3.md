# Xtate 3.0.0-rc.3

This is a **release candidate** for hands-on trial, not the final 3.0.0. The
final release waits for user testing and fixes.

RC.3 focuses on the console redesign and on removing the file and log
rough edges reported against RC.2.

## Changes since 3.0.0-rc.2

### Console redesign

- Readable **Paper** theme by default (large type, warm surfaces, stronger
  contrast) with an optional **Graphite** dark theme. Theme, density and live
  refresh are saved per browser.
- **Live scan** now leads with a large status headline (`Scanning`,
  `Scan complete`, `Scan failed`, cancelled, timed out or stalled), counters and
  a terminal explanation. The progress bar was removed; the state and counters
  are the authoritative status.
- Worker log tails are cleaned of terminal control fragments but keep genuine
  `[HIN]`, `[ERR]` and similar prefixes.
- **Open log** and **Open result** ask the server to open the job's resolved log
  or result file with the operating system's default program. The server
  accepts only a job id and a file kind; the browser never supplies a path.
- **Modules** is grouped into Scan engines, Protocol probes, Output writers and
  Target generators, with counts, search and type tabs.
- **Settings** was replaced by **System & preferences**: Appearance, Runtime,
  Capabilities and the local Security model.
- Starting a scan switches to Live immediately, resets the previous job's log,
  records and polling state, and shows the current job without stale data.
- Module parameters can be edited directly in the Method panel; values are sent
  as `scan_args`/`probe_args`. If the controls do not cover a parameter, the CLI
  and MCP still expose the full argument set.

### Files and lifecycle

- Results and request files now live in a managed state directory:
  `%LOCALAPPDATA%\xtate` on Windows, or
  `$XDG_STATE_HOME/xtate`/`$HOME/.local/state/xtate` on Linux. `XTATE_STATE_DIR`
  overrides the root. New jobs no longer write result files into the current
  directory.
- Request and heartbeat files are removed when a job reaches a terminal state.
- Fixed Unicode heartbeat writes on Windows: heartbeat updates now use wide
  paths, so non-ASCII state directories no longer leave `.heartbeat.tmp` files.
- Fixed generated result paths being JSON-unescaped on Windows (backslashes in
  `C:\Users\...` are no longer consumed as escape sequences).

### MCP and control plane

- Private `xtate --gui`, `xtate --tui` and `xtate --mcp` sessions generate an
  ephemeral control token when the environment does not already set one.
- MCP adds `capabilities`, `iface.list`, `preflight` and bounded `job.records`;
  result records support plain files, manifest chunks and zstd-compressed
  chunks.
- MCP audit logging is opt-in through `XTATE_MCP_AUDIT_LOG`; the server no
  longer writes an audit log into the current directory by default.

## Compatibility

- CLI and MCP request shapes are unchanged except for the added tools and
  capabilities.
- Existing `--control-plane` deployments keep their current token policy; the
  ephemeral token applies only to private GUI/TUI/MCP sessions.
- Result paths supplied by a client are still used exactly as supplied; default
  paths now resolve into the managed state directory.
- TUI is deprecated in 3.0 and remains only for 2.44 compatibility.

## Verification

- Windows MSVC release build, self-test and regression test pass.
- Full Windows suite: i18n parity/coverage, schema/module validation, JSON
  schema runtime, generate, control, MCP, MCP stability, TUI and GUI.
- Linux build with ngtcp2/GnuTLS reports `http3:true` and
  `quic_transport:true`; Linux suite passes i18n, generate, control, MCP, MCP
  stability, TUI and GUI.
- GUI tests cover preflight validation, managed state, result paging, open-file
  rejection cases and private-token enforcement.
- Documentation checks: no broken relative links in English or Chinese manual.

## Known limitations

- HTTP/3 and QUIC transport remain Linux-only; Windows reports them unavailable
  through `--list-capabilities`, MCP and the console.
- Preflight is authoritative for the fields it validates, but it does not bind a
  request hash to `job.start` yet.
- `include_file` route grouping and MCP generate/stream input remain future
  work.
- The console does not provide per-job disk quota controls or a byte-level
  result editor.
- The final 3.0.0 is not released. Please trial RC.3 and report defects.
