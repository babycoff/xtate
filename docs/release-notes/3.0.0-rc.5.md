# Xtate 3.0.0-rc.5

Release date: 2026-11-14

This release candidate is a usability and verification pass over the 3.0
console. It does not change the scanning engines or the wire format.

## Changes since 3.0.0-rc.4

### The console no longer launches a browser

`xtate --gui` now prints the URL, the private control endpoint and the
per-session token, then waits. It never calls `ShellExecute`, Explorer, or any
browser process. Open the printed address yourself in the browser you prefer.

The old `--gui-no-open` flag is retained only for script compatibility; it is
deprecated and has no effect.

### Faster Open log / Open result

On Windows, the **Open log** and **Open result** actions now start Notepad
directly with `CreateProcessW` and the resolved job path. They no longer wait
for ShellExecute/DDE/Explorer association resolution. In a local measurement the
`/api/open` request returned in 224 ms, including PowerShell client overhead.

The server still resolves the path from the job's own status/manifest and never
accepts a client-supplied path.

### Complete module help and probe transport

Expanded module cards now show the full long description and the complete
parameter table. Probe modules (and scans that require a probe) display a
transport badge: `TCP`, `UDP`, or `TCP · stateful`, plus a translated
`Probe type` line. The Modules page remains grouped by the real Xtate taxonomy:

- Scan modules
- Probe modules
- Output modules
- Generate modules

### README and project front page

The English and Chinese READMEs were rewritten around the 3.0 experience: RC
status, a Start-here table, a console screenshot, current module counts, GUI and
MCP entry points, bounded `job.records`, and the new protocol/capability
reporting. The README no longer advertises browser auto-open or the retired TUI
workflow.

### MCP and Agent Skill contract fixes

An independent MCP contract review found three blocking mismatches. They are
fixed in rc.5:

- `start_scan` now has a flat input schema. Its tool arguments are the
  scan-request fields directly; clients no longer wrap them in an extra
  `arguments` object. The skill and examples match this shape.
- `preflight` accepts `targets` and `ports` as either JSON arrays or
  comma-separated strings, matching both MCP clients and the GUI form.
- tools/call requests over the 8 KiB line buffer now return a clear
  `request too large; ... use include_file` error instead of a misleading
  authorization failure.

`validate_config` and `start_scan` reject unknown scan-request fields, and MCP
validates `global_args` values before forwarding them to the control plane.

### Build-environment plan

The 3.0 roadmap now includes an Ubuntu 24.04 full-feature build environment:
a Docker image with all optional dependencies, mainland-China package-mirror
selection, Linux capability smoke tests, and host access to a GUI running inside
the container. This is a plan for the next infrastructure milestone, not part of
the RC.5 binary.

## Compatibility

No scan-request or result-schema changes. Jobs and manifests written by rc.4
remain readable. `--gui-no-open` is accepted but deprecated. Scripts that
expected the GUI to open a browser should open the printed URL themselves.

## Known limitations

- HTTP/3 and QUIC transport remain Linux-only with ngtcp2/GnuTLS; Windows
  reports them as unavailable.
- The GUI writes results under the visible `<exe-dir>/xtate-state/runs/`
  directory by default and falls back to the per-user state directory when the
  executable directory is not writable.
- Global parameters exposed by the GUI are limited to the audited 23-option
  allowlist; other options remain CLI-only.
- Result browsing is bounded to 200 records per request.
- The control plane remains local-only; its token is optional for an explicitly
  started daemon, but private GUI/MCP/TUI control planes generate an ephemeral
  token automatically.
- The Ubuntu 24.04 build image is planned, not shipped in this candidate.

## Trial focus

Please exercise the GUI on Windows and Linux:

1. `xtate --gui`, open the printed address, switch English/中文.
2. Start a small authorized scan and confirm Live state, counters, log tail and
   bounded records.
3. Use **Open log** and **Open result**; confirm they open immediately.
4. Expand several scan and probe modules and check the full help/probe type.
5. Run one MCP client and the Agent Skill workflow if available.

The final 3.0.0 release waits for field-trial feedback.
