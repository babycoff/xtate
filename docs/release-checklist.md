# Surface Synchronization Checklist

Xtate exposes the same capabilities through several deliberately separate
surfaces: the CLI and its help, the MCP server, the browser console, the Docker
image, and the English/Chinese documentation. A change that reaches users must
be reflected on every surface that describes it. This page is the short,
reviewable list; `tests/release/test_surface_consistency.py` enforces the parts
that can be checked mechanically.

Run the gate before opening a pull request:

```bash
python3 tests/release/test_surface_consistency.py --binary ./bin/xtate
```

The test is read-only. It compares the built binary with the repository text,
so build before running it. It runs in the Linux integration and Windows CI
jobs.

## New global parameter

| Surface | What to update |
|---|---|
| Parser | `config_parameters[]` in `src/xconf.c`, plus `SET_*`/echo handling if stateful. |
| English help | Long and short description in the same entry. State the default only if it is the code default. |
| Chinese help | `i18n_global_help[]` in `src/util-misc/i18n.c` (otherwise Chinese falls back to English). |
| Usage examples | Add a `--usage` example only if the parameter changes a common workflow. |
| GUI | Expose it through `/api/options` if it is a safe global control; otherwise leave it CLI/MCP-only and say so. |
| MCP | Add it to the flat `start_scan` schema in `src/util-scan/mcp-server.c` only when agents need it; keep the CLI as the complete surface. |
| Docs | `docs/help-i18n.md`, the relevant page in `docs/`, and the Chinese counterpart. |
| Tests | At least a parse/default test; add a surface test expectation if the help count changes. |

Prefer one parameter over several aliases. Aliases belong in the `alias` array
and must not create a second help entry.

## New module (scan, probe, output, or generate)

| Surface | What to update |
|---|---|
| Registry | Module definition and registration in the matching `src/*-modules/` file. |
| Help | Module description and every parameter description; verify with `--help-scan|probe|out|gen <name>`. |
| Counts | Windows and full-Linux counts in `README.md`, `docs/modules.md`, and any page that quotes them. |
| MCP | `list_modules`, `describe_probe`, and `start_scan` work from the registry; no second hard-coded list. Update `docs/mcp-server.md` only if the tool contract changes. |
| GUI | The module catalog is served by `/api/modules`; update `docs/gui.md` only if the rendering contract changes. |
| Docker | The Ubuntu image builds optional modules from source; check `docker/ubuntu24-build/Dockerfile` and capability output if the module adds a dependency. |
| Tests | Add the module to the relevant schema/module validator expectation and a minimal behavioral test. |

Module help is user-facing text. Run the module help command and read it; a
successful compile does not prove the help is correct.

## Version change

Version changes touch more files than any other edit:

- `CMakeLists.txt` (`project(... VERSION ...)` and `XTATE_VERSION_SUFFIX`).
- `src/version.h` is generated by CMake from `src/version.h.in`; never edit it by
  hand in a normal build. A stale committed copy is caught by the surface gate.
- `README.md` and `README.zh-CN.md` badges and “current release” text.
- `docs/README.md`, `docs/zh-CN/README.md`, `docs/getting-started.md`,
  `docs/zh-CN/getting-started.md`, `docs/known-limitations.md`, and any page
  that says “current version”.
- `docs/release-notes/<version>.md` and the Chinese counterpart.
- `BUILD-INFO` is generated by the packaging scripts; do not hand-edit it.

Historical release notes keep their original version. Do not rewrite them when
bumping the current version.

## New GUI route or MCP tool

| Surface | What to update |
|---|---|
| Code | `src/util-scan/gui.c` route table or `tools_json` in `src/util-scan/mcp-server.c`. |
| Docs | `docs/gui.md` or `docs/mcp-server.md`; Chinese counterpart. |
| Contract test | `tests/gui/test_gui.py` or `tests/mcp/test_mcp_contract.py`. |
| Security | Loopback/Host/token checks for GUI routes; authorization and argument limits for MCP tools. |

The surface gate compares route names and tool names with the docs. It does not
prove authorization behavior; contract tests do that.

## New dependency or build option

- `CMakeLists.txt` option and `NOT_FOUND_*` fallback.
- `README.md` build table, `docs/getting-started.md`, platform/dependency pages.
- `docker/ubuntu24-build/Dockerfile` and the capability output.
- CI build matrix: at least one reduced build and one full build.
- The build must still succeed when the dependency is absent.

## Release sequence

1. Update the version and release notes.
2. Run the surface gate, version-consistency test, and full test tiers for the
   changed platform.
3. Build Windows and Linux release artifacts; record SHA256 sums.
4. Verify the archive smoke test on a clean host (`--version`, `--selftest`).
5. Publish only the RC; the final release waits for maintainer sign-off.
6. After publishing, re-download the assets and check the recorded hashes.
